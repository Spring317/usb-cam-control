\begin{abstract}
This document details the software architecture, USB Picture Transfer Protocol (PTP/ISO 15740) data acquisition pipeline, and UML diagrams for the Canon EOS R8 FastAPI control system. We provide a clean UML Use Case Diagram detailing system boundaries and actor interactions, as well as a full UML Sequence Diagram mapping the exact lifecycle of binary data extraction—from client HTTP dispatch, thread mutex locking, and viewfinder muting to PTP USB bulk data retrieval and image frame presentation.
\end{abstract}

\section{System Data Flow Architecture}

The system connects a web-based user interface to physical camera hardware via an asynchronous FastAPI backend and low-level \texttt{libgphoto2} PTP drivers.

The complete system layer breakdown consists of:
\begin{enumerate}[label=\arabic*.]
    \item \textbf{Frontend UI (Browser):} HTML5/JavaScript dashboard managing live preview displays and user interaction controls.
    \item \textbf{Backend API (FastAPI):} Asynchronous web application handling routing, CORS, HTTP response streams, and endpoint contracts.
    \item \textbf{Controller Layer (\texttt{CameraController}):} Python thread-synchronized wrapper interfacing with \texttt{python-gphoto2} bindings and managing hardware locks.
    \item \textbf{Hardware \& Protocol Layer (\texttt{libgphoto2} / USB PTP):} USB bulk endpoints transferring operational data packets to/from Canon EOS R8 SDRAM and CMOS sensor assemblies.
\end{enumerate}

\section{UML Use Case Diagram}

Figure~\ref{fig:uml_usecase} illustrates the UML Use Case Diagram modeled after standard camera control software patterns. Actors are placed strictly outside the system boundary, and all use cases are cleanly separated into two distinct functional columns with generous vertical spacing.

\subsection{Actor Definitions}
\begin{itemize}
    \item \textbf{User / Web UI (Primary Actor):} Interacts with the web browser to trigger capture commands, view live streams, and modify settings.
    \item \textbf{Canon EOS R8 Camera (Secondary Actor):} Receives low-level PTP operational codes and transfers image data over USB endpoints.
    \item \textbf{Linux V4L2 Device (Secondary Actor):} Receives video stream buffers piped directly via \texttt{ffmpeg}.
\end{itemize}

\section{Data Extraction and Preview Mechanics}

\subsection{PTP Capture Target and In-Memory Storage}
Upon connection initialization, the controller sets \texttt{capturetarget = 1}. This directs the DIGIC X processor to store image data directly in volatile camera SDRAM buffer space rather than flushing to physical SD card memory, preventing file system locks.

\subsection{C-Python Buffer Pointer Retrieval}
The binary transfer is executed cleanly without unnecessary file system overhead:
\begin{lstlisting}[language=Python]
# Allocate raw C memory file container wrapper
camera_file = gp.CameraFile()

# Fetch binary buffer directly over USB Bulk IN Endpoint
self.camera.file_get(file_path.folder, file_path.name, 
                     gp.GP_FILE_TYPE_NORMAL, camera_file, self.context)

# Flush binary data buffer to target path
camera_file.save(target_path)
\end{lstlisting}

\subsection{Live Preview Frame Extraction}
For real-time streaming, the backend continuously pulls preview frames from the viewfinder buffer memory via \texttt{capture\_preview()}:
\begin{lstlisting}[language=Python]
def capture_preview(self):
    with self.lock:
        camera_file = gp.CameraFile()
        self.camera.capture_preview(camera_file, self.context)
        file_data = camera_file.get_data_and_size()
        return memoryview(file_data).tobytes()
\end{lstlisting}
The FastAPI generator packages these frame buffers into an HTTP stream (`multipart/x-mixed-replace; boundary=frame`) refreshed at $\approx 20\,\text{FPS}$.
